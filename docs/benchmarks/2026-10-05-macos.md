# Stock OpenJDK native transport comparison, 2026-10-05

Bemo did not consistently beat Netty's native kqueue transport in this run.
Bemo/Netty median throughput ratios were 0.73–0.99. The largest gap was the
64 KiB identity response over shared JDK TLS: Bemo achieved 0.73 times Netty's
throughput, with all three paired samples below 0.79.

| Payload | Encoding | TLS | Bemo / kqueue throughput |
| --- | --- | --- | --- |
| 1 KiB | identity | none | 0.88 |
| 64 KiB | identity | none | 0.96 |
| 1 KiB | gzip | none | 0.89 |
| 64 KiB | gzip | none | 0.99 |
| 1 KiB | identity | JDK | 0.99 |
| 64 KiB | identity | JDK | 0.73 |
| 1 KiB | gzip | JDK | 0.98 |
| 64 KiB | gzip | JDK | 0.98 |

[Machine-readable samples and ratios](2026-10-05-macos.json) include p50/p99,
process CPU, selected driver, and fallback state. These are short closed-loop
measurements on a shared macOS 26.6.2 arm64 workstation, using stock OpenJDK
25.0.2, two I/O threads, four persistent clients, three fresh JVM samples,
500 warmup and 2,500 measured requests per client. Transport order rotates per
sample. Both transports use the same codecs, payloads, heap, hostname verification,
and JDK TLS 1.3 configuration. Bemo selected kqueue without AUTO fallback.

This run preceded commit `93ee43e2ccde4f84a12361ca47aacda5f26d04f4` and used
its final benchmark implementation; the subsequently added FFI header metadata,
compatibility checks, and documentation do not change the measured data plane.
It reports no confidence interval and does not establish Linux epoll performance.
RSS is unavailable on this host and is recorded as null. A native Rust TLS run
is a separate comparison because it changes the TLS provider.

To repeat, set `BEMO_BENCH_JAVA` to the stock OpenJDK executable, then run
`make bench-prepare` and `python3 tools/bench.py run`. See
[measurement controls and limitations](../measurement.md).
